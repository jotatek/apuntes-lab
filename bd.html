Datos, información y conocimiento

ConceptoDefiniciónEjemplo
DatoHecho, evento o transacción registrado"22 ºC"
InformaciónDatos procesados y comunicados para poder interpretarlos"22 ºC en Sevilla el 15 de julio"
ConocimientoInformación asimiladaSaber que hace calor en verano
💡
Los datos necesitan contexto (normalmente más datos) para convertirse en información.

Sistema de información

Conjunto de elementos destinados al tratamiento y administración de datos e información, organizados para su uso posterior y creados para cubrir un objetivo. Puede estar informatizado o no.

📝 Mis notas
02

Ficheros

Forma primitiva de almacenar información. Problemas: aplicaciones "acopladas" a los ficheros (dependencia físico-lógica), difícil compartir datos entre aplicaciones, sin acceso concurrente.

Tipos y formatos

  • Texto (planos) o binario.
  • Formatos: CSV, JSON, XML, Parquet, Avro.
  • Se identifican por nombre + extensión (clientes.csv).

Definición formal y estructuras

  • Fichero: secuencia de números binarios que organiza información relacionada con un mismo aspecto.
  • Registro: estructura lógica que agrupa los datos de un mismo elemento (un estudiante = un registro).
  • Campo: información elemental dentro de un registro (nombre, email).

Tipos de acceso

Secuencial

Registros uno tras otro. Para llegar a uno hay que recorrer los anteriores. Ej: cintas magnéticas.

Encadenados

Secuenciales: cada registro guarda un puntero con la dirección del siguiente.

Indexados

Dos zonas: datos (secuencial) + índices (clave + dirección), como el índice de un libro.

Directo / Aleatorio

Se salta directamente al registro deseado.

Operaciones

  • Abrir/cerrar, leer/escribir, posicionarse.
  • Fragmentación y compactación: si un registro no se guarda consecutivo está fragmentado; compactar mejora la eficiencia.
  • Compresión: reduce tamaño.
  • Cifrado: hace el contenido ilegible.
⚠️
Hoy los ficheros se limitan a datos específicos de aplicaciones (configuración, datos privados) sin acceso concurrente.

03

Bases de datos y modelos

Definición

Conjunto de datos interrelacionados, con características de integridad y redundancia mínima, accesibles por varios usuarios y aplicaciones. Toda BD debe permitir insertar, modificar y borrar datos.

  • Integridad: los datos son correctos y completos.
  • Redundancia mínima: cada dato existe en un único lugar.
  • Contiene datos y metadatos (diccionario de datos).

Ventajas e inconvenientes

Ventajas

Independencia datos-programas · menor redundancia · integridad · mayor seguridad · metadatos · acceso más eficiente · menos espacio · acceso concurrente.

Inconvenientes

Instalación costosa · personal cualificado · implantación larga · ausencia de estándares reales.

Clasificación

CriterioTipos
ContenidoInfo actual, directorios, documentales
UsoIndividual, compartida, acceso público, propietarias
VariabilidadEstáticas, dinámicas
LocalizaciónCentralizadas (anfitrión, cliente/servidor), distribuidas
Organismo productorPúblicas, sin ánimo de lucro, privadas, cooperación
AccesoLocal, en red, en línea (web/API), cloud
CoberturaCientífico-técnicas, económico-empresariales, sanitarias…

Modelos de datos

Conjunto de herramientas conceptuales para describir datos, relaciones, semántica y restricciones.

Tipos NoSQL

Clave-valor

Acceso solo mediante clave.

Documental

Documentos JSON con info de varias entidades.

Grafos

Nodos y vértices.

Columnas

Vectorial

04

Sistemas Gestores de Bases de Datos (SGBD)

Software que permite crear, manipular y administrar bases de datos. Oracle, MySQL, MariaDB, LibreOffice Base, Access, MongoDB, PostgreSQL son SGBD, no bases de datos. Actúan de interfaz entre usuario y BD.

Funciones

  1. Independencia de los datos respecto a aplicaciones y usuarios.
  2. Eficiencia y seguridad (control de permisos).
  3. Integridad: detectar operaciones erróneas, permitir transacciones.
  4. Acceso concurrente.
  5. Administración: copias, recuperación, usuarios y permisos, monitorización.

Propiedades ACID

LetraPropiedadSignificado
AAtomicidadTodas las operaciones de la transacción o ninguna.
CConsistenciaLa BD pasa de un estado válido a otro válido.
IAislamientoUna transacción no afecta a otras; no se ven versiones intermedias.
DDurabilidadFinalizada la operación, los datos no se pierden.

Componentes

  • Diccionario de datos: metadatos (estructuras, relaciones, restricciones, cuentas, permisos).
  • Espacio de datos: donde se guardan los datos (Oracle: tablespaces).
  • Herramientas (rol DBA): lenguajes DDL (definición), DCL (control), DML (manipulación); recuperación (failover); copias; exportación/importación; distribución de datos.
💡
Truco: DDL = crear/alterar tablas. DML = insert/update/delete/select. DCL = grant/revoke.

05

Arquitectura de 3 niveles (ANSI/SPARC)

Propuesta en los años 70. Objetivo: separar aplicaciones de datos, permitir distintas vistas y usar un catálogo para el esquema.

NivelEsquemaDescripción
ExternoEsquema externoLo más cercano al usuario: salida de datos (formulario, listado, informe). Cada programa ve solo parte de la BD.
ConceptualEsquema conceptualUnión de todos los datos y relaciones; representación lógica (en relacionales, tablas).
Interno / FísicoEsquema físicoAlmacenamiento y formas de acceso: archivos, ubicación, organización.

Entre niveles hay funciones de traducción (externo → conceptual → físico).

Aporta

Independencia lógica

Modificar el esquema conceptual sin reescribir esquemas externos ni aplicaciones.

Independencia física

Modificar el esquema interno sin alterar el conceptual ni los externos (ej.: reorganizar archivos para mejorar rendimiento).

06

Perfiles, arquitecturas físicas y legislación

Perfiles de usuario

  • Usuario final: usa los datos a través de una aplicación.
  • Analista / Ingeniero de datos: diseña arquitecturas (lógico y físico).
  • Desarrollador: crea aplicaciones; consultas, inserciones, borrados.
  • DBA: administrador del SGBD. Codifica esquemas, asigna permisos, vela por la seguridad y el mantenimiento.

Arquitecturas físicas

Centralizada monousuario

Un solo ordenador, sin concurrencia. MS Access.

Centralizada cliente-servidor

Datos en servidor (VPS o cloud) y aplicaciones clientes con conexión remota. MySQL, PostgreSQL, Oracle.

Distribuida

Datos repartidos entre varios servidores (replicando, particionando o fragmentando). Más robusta pero más compleja. Oracle Cloud, MongoDB, Redis.

Legislación

  • RGPD 2016/679: marco europeo de protección de datos personales.
  • LOPDGDD 3/2018: adapta y complementa el RGPD en España (incluye derechos digitales: desconexión digital, testamento digital).

Datos sensibles (art. 9 RGPD)

Origen racial/étnico · ideología · afiliación sindical · religión · orientación sexual · salud · datos genéticos · datos biométricos de identificación unívoca.

Solo se tratan con consentimiento explícito o excepciones legales. No deben recogerse salvo estricta necesidad.

Obligaciones del responsable

  1. Recogida y consentimiento previo, explícito, informado, claro, libre, específico.
  2. Transparencia (política de privacidad, aviso legal).
  3. Derechos: acceso, rectificación, supresión, portabilidad, oposición y limitación.
  4. Calidad y actualización de los datos.
  5. Seguridad (medidas técnicas y organizativas; cifrado y anonimización).
  6. DPIA si hay alto riesgo.
  7. Responsabilidad proactiva (registro de actividades, DPO si procede).
  8. Transferencias internacionales: país adecuado o cláusulas contractuales estándar.
  9. Brechas: notificar a la AEPD en 72 horas.
  10. Secreto profesional.
  11. Formación y auditorías.
  12. La carga de la prueba recae en la empresa.

Infracciones LOPDGDD

GradoEjemplosPrescripción
Leves (art. 74)Incumplimientos formales1 año
Graves (art. 73)Tratar datos sin contrato, no adoptar medidas, no notificar brecha2 años
Muy graves (art. 72)Tratar sin base jurídica, vulnerar principios, tratar categorías especiales, impedir derechos3 años

Sanciones (art. 83 RGPD)

Hasta 10 M€ o 2%

Incumplir obligaciones del responsable/encargado.

Hasta 20 M€ o 4%

Infringir principios básicos, condiciones del consentimiento o derechos de los interesados.

07

Diseño de BD y modelo Entidad-Relación

Objetivo del diseño

Una BD bien estructurada y eficiente que cumpla los requisitos. Cinco objetivos comunes: coherencia e integridad, mantenibilidad, rendimiento, seguridad, escalabilidad. El primer paso (más crítico) es determinar los requisitos.

Las 3 fases del diseño

FaseEntradaModeloResultado
ConceptualMundo real / requisitosE-R (EER)Esquema conceptual
LógicaEsquema conceptualRelacionalEsquema lógico / canónico
FísicaEsquema lógico + SGBDDDL de SQLEsquema físico / interno

Modelo E-R

  • Modelo conceptual de alto nivel, propuesto por Peter Chen en 1976.
  • Los modelos conceptuales son incompletos: no captan toda la semántica del mundo real.
  • No es un único modelo, sino una familia (muchas extensiones).

Símbolos del diagrama E-R

Rectángulo

Entidad

Elipse

Atributo

Rombo

Relación

Línea

Unión (atributo-entidad, entidad-relación)

Si la relación tiene atributos, se unen al rombo. En la notación de flechas: la punta indica el lado del uno; sin punta, el muchos.

Nomenclatura

  • Sin espacios ni tildes.
  • Entidades: sustantivos, singular, MAYÚSCULAS. Compuestas con guion bajo: LINEA_PEDIDO.
  • Atributos: singular, minúsculas, camelCase (nombreCompleto).
  • Relaciones: verbos en MAYÚSCULAS (COMPRAR).

Propiedades del modelo

Estáticas

Restricciones comprobables mirando la BD en un instante (valores, no nulo, identificación, cardinalidad).

Dinámicas

Operaciones, transacciones y evolución. Ej: "una matrícula anulada no puede volver a estar activa".

💡
Truco: ¿se puede comprobar mirando un solo instante? → estática. ¿Hay que comparar el valor anterior con el nuevo? → dinámica.

Método para elaborar el modelo

  1. Leer y comprender el problema.
  2. Localizar entidades (sustantivos) y relaciones (verbos). Dos sustantivos unidos por un verbo ⇒ dos entidades y una relación.
  3. Extraer atributos, evitando duplicidad; comprobar identificador.
  4. Ver si algún atributo debe ir en la relación en vez de en la entidad.
  5. Definir cardinalidades: primero la máxima, luego la mínima; comprobar si las entidades son fuertes o débiles.
  6. Revisar: relaciones redundantes o atributos derivados.

08

Entidades, atributos y claves

Entidades

  • Entidad: cualquier objeto con existencia independiente del que se guarda información.
  • Conjunto de entidades: grupo del mismo tipo (no tienen por qué ser disjuntos).
  • Ocurrencia (instancia): un elemento concreto de la entidad.
  • Control de redundancia: una entidad solo aparece una vez en el modelo.

Entidades fuertes y débiles

Fuertes (regular)

Rectángulo simple. Existe por sí misma. ALUMNO, CLIENTE.

Débiles

Rectángulo doble. Su existencia depende de otra entidad y se relaciona 1:N. NOTAS depende de ALUMNO.

Dos tipos de dependencia:

  • Existencia (E): no puede existir sin la fuerte. Cardinalidad mínima = 1.
  • Identificación (ID): además, no se identifica por sí misma, sino con los identificadores de la fuerte. Marca con ID o rombo doble. Ej: LINEA_PEDIDO se identifica por numero + codigo del PEDIDO.

Una entidad puede ser débil en una relación y fuerte en otras (por eso se marca también la relación con doble rombo).

Atributos

TipoDescripciónRepresentación
Identificador (clave)Único; identifica ocurrenciasSubrayado
CompuestoAgrupa varios atributos (dirección = calle, número, piso…)Elipses conectadas; nombre entre paréntesis
MultivaluadoVarios valores (teléfono: fijo, móvil)Doble elipse
DerivadoSe calcula a partir de otros (edad desde fnac)Elipse punteada
OpcionalAdmite nulos (email)(0) junto al nombre

Tipos de claves

ConceptoDefiniciónEjemplo
SuperclaveConjunto que identifica de forma única{DNI, nombre, dirección}
Clave candidataSuperclave con el mínimo de camposDNI, nº SS
Clave primaria (PK)Candidata elegida: sin nulos, sencilla, estable. Va subrayadaDNI
Clave alternativaCandidatas no elegidas (subrayado troceado)Pasaporte

Requisitos de un buen identificador

  • Único, siempre con valor (sin nulos), estable, sencillo/corto y sin redundancia.
  • Ejemplo USUARIO(login, password, email, nombre, telefono): candidatos son login y email. Se elige login porque el email puede cambiar.

09

Relaciones y cardinalidades

Relación

  • Asociación entre entidades; nombre de verbo; rombo. Tiene dos sentidos.
  • Atributos en la relación: guardan información que no es propia de ninguna entidad (ej.: FECHA_OPERACIÓN en CLIENTE-OPERA-CUENTA). Suelen esconder una entidad asociada.

Grado

GradoTipoEjemplo
1Reflexiva (unaria)EMPLEADO jefe de EMPLEADO
2Binaria (la más común)PROVEEDOR-SUMINISTRA-ARTÍCULO
3TernariaCLIENTE-TIENE-CUENTA-SUCURSAL
4+N-aria (muy excepcional)—

Cardinalidad de participación

Mide la obligatoriedad de la correspondencia. Notación: Card(E, R) = (mín, máx).

ValorSignificado
(0,1)Ninguna o una
(1,1)Siempre exactamente una
(0,N)Ninguna o muchas
(1,N)Una o muchas

Para averiguarla: coge una ocurrencia de una entidad y pregúntate con cuántas de la otra se relaciona.

Ejemplo PRODUCTO-CATEGORIA:

  • Card(PRODUCTO, PERTENECER) = (1,1): un producto pertenece siempre a una categoría.
  • Card(CATEGORIA, PERTENECER) = (0,N): una categoría puede no tener productos, o muchos.

Tipos de relaciones binarias (según las máximas)

1:1

Un elemento se corresponde con uno solo de la otra y viceversa. Ej: GRUPO-PERTENECE-AULA.

1:N

Uno de la primera se corresponde con varios de la segunda, y cada uno de la segunda con uno de la primera. Ej: PROVEEDOR-ARTÍCULO.

N:M

Cada elemento se corresponde con varios de la otra. Ej: VENDEDOR-ARTÍCULO.

N:M con fechas

Una N:M simple solo permite una ocurrencia por pareja. Soluciones:

  1. Atributo multivaluado fecha en la relación.
  2. Crear una entidad débil (ej. PRESTAMO) con restricción de ID respecto a LIBRO y USUARIO.

Relaciones reflexivas y roles

La misma entidad cumple dos roles. Ej: EMPLEADO-TRABAJAR con roles trabajador (1,N) y jefe (0,1) → relación 1:N. El rol es la función que cumple una entidad en una relación concreta.

Notaciones

  • Chen: regla Entidad, Relación, Cardinalidad, Entidad. La cardinalidad se anota en el extremo opuesto de la entidad a la que se refiere.
  • Pata de gallo: ○ anillo = cero · | guion = uno · pata de gallo = muchos.
  • UA: rombo negro = N:M · mitad negro = 1:N · vacío = 1:1.

Pérdida expresiva (semántica)

Cuando el modelo no puede expresar una restricción, relación o regla de negocio. Se documenta con notas de diseño (PE). Formato: PE: "Un empleado no puede ser jefe de su propio departamento".

10

Modelo E-R Extendido (EER)

A mediados de los 80 se añadieron clase/subclase, generalización/especialización y agregación.

Generalización / especialización

  • Superclase (padre): características comunes.
  • Subclases (hijas): características propias de cada especialización.
  • Toda ocurrencia de una subclase es también de la superclase.
  • Herencia: atributos e interrelaciones del padre se propagan a los hijos.
  • Relación ES-UN (IS-A): un CAMION es un VEHICULO.

Ejemplo: LIBRO(isbn, título) → EBOOK(formato) y EN_PAPEL(numPaginas).

Representación

  • Siempre en vertical: superclase arriba, subclases debajo.
  • Círculo con d (disjunta) o o (solapada).
  • Línea entre padre y círculo: simple = parcial, doble = total.
  • Del círculo a los hijos: línea con un arco indicando el sentido.

Tipos de especialización

Total

La superclase pertenece obligatoriamente a alguna subclase.

Parcial

Puede no pertenecer a ninguna.

Disjunta / exclusiva

Solo una subclase a la vez.

Solapada

Varias subclases a la vez.

Agregación

  • Surge de que el modelo E-R no permite relaciones entre relaciones; evita las ternarias.
  • Se agregan dos entidades y su relación para obtener una entidad asociativa.
  • La entidad asociativa no tiene identificador propio: se identifica por las entidades que asocia (como una entidad débil).
  • Frente a una ternaria: la agregación remarca la relación entre una pareja de entidades.

Ejemplo: DOCENTE-IMPARTIR-AULA forman la entidad asociativa SESION (un docente en un aula). Para registrar incidencias: SESION-REGISTRAR-INCIDENCIA.
